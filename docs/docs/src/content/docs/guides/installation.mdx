# Installation

One command puts the framework in place: routing, validation, dependency
injection, the response builder, and the middleware stack. The heavier pieces
(the ORM, JWT, templating, Redis) are optional extras you add when the product
needs them, so the dependency tree stays proportional to what you build.

## Requirements

- Python 3.10 or newer
- Basic familiarity with `async` / `await`

Nothing else. [`uv`](https://docs.astral.sh/uv/) is recommended below and is
what the rest of these guides use, but every command has a `venv` and `pip`
equivalent that needs no third-party tool.

Check your Python version:

```bash
python --version
```

## Create a project

<Tabs syncKey="pkg">
  <TabItem label="uv (recommended)">

    ```bash
    uv init my-sillo-app
    cd my-sillo-app
    uv add sillo-framework
    ```

    This writes a `pyproject.toml`, creates `.venv`, and records both the
    dependency and an exact `uv.lock`. Run anything inside the environment
    without activating it:

    ```bash
    uv run sillo --version
    uv run python -c "import sillo; print(sillo.__version__)"
    ```

    Do not have `uv` yet?

    ```bash
    # macOS / Linux
    curl -LsSf https://astral.sh/uv/install.sh | sh

    # Windows
    powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
    ```

  </TabItem>
  <TabItem label="Poetry">

    ```bash
    poetry new my-sillo-app --src
    cd my-sillo-app
    poetry add sillo-framework
    ```

    Or, in a directory you already have:

    ```bash
    poetry init          # answer the prompts, or --no-interaction
    poetry add sillo-framework
    ```

    `poetry add` resolves, installs, writes `poetry.lock`, and records the
    dependency in `pyproject.toml`. Run inside the environment with:

    ```bash
    poetry run sillo --version
    ```

    Or open a shell in it once: `poetry env activate` on Poetry 2.x,
    `poetry shell` on 1.x.

  </TabItem>
  <TabItem label="venv + pip">

    ```bash
    mkdir my-sillo-app && cd my-sillo-app
    python -m venv .venv
    source .venv/bin/activate        # Windows: .venv\Scripts\activate
    pip install sillo-framework
    ```

    `venv` and `pip` ship with Python, so this needs nothing installed first.
    With the environment activated, commands are typed as they appear, `sillo
    --version`, no prefix.

    Nothing records what you installed, so pin it yourself:

    ```bash
    pip freeze > requirements.txt
    ```

    Reproduce it later with `pip install -r requirements.txt`.

  </TabItem>
</Tabs>

:::tip[Use uv if you have no reason not to]
It resolves and installs far faster than the alternatives, manages the Python
version as well as the packages, and needs no separate step to create or
activate an environment. Everything in these guides is written against it.

Sillo does not care either way. It is an ordinary package with a standard
`pyproject.toml`, so PDM, Hatch, Pipenv or a bare `venv` all work. Nothing in
the framework reads a lockfile or shells out to a package manager.
:::

:::note
Every later example is written as a bare command: `sillo db:migrate`. Prefix it
with `uv run` under uv, or `poetry run` under Poetry. With an activated `venv`,
type it as written.
:::

## Create your first app

Create `main.py`:

```python
from sillo import SilloApp

app = SilloApp()


@app.get("/")
async def home(request, response):
    return response.json({"message": "Hello from Sillo"})
```

Run it:

```bash
sillo serve main:app --reload
```

Open:

```text
http://127.0.0.1:8000
```

You should see:

```json
{"message": "Hello from Sillo"}
```

## Existing projects

Install it into whatever the project already uses:

```bash
uv add sillo-framework            # uv
poetry add sillo-framework        # Poetry
pip install sillo-framework       # venv + pip
```

Sillo does not care which. It is an ordinary package with a standard
`pyproject.toml`, so it installs the same way anything else does.

## Upgrading from 0.0.1a15 or earlier

The application class was renamed from `silloApp` to `SilloApp`. Classes in Python are `CapWords`, and the old spelling made `app = silloApp()` read like a function call at every entry point.

The migration is one find-and-replace:

```python
from sillo import SilloApp

app = SilloApp(title="Projects API")
```

<Aside type="danger" title="`silloApp` no longer exists">
Do this before you upgrade. `silloApp` was removed in **0.0.2a2**. There is no
alias and no deprecation period left, so `from sillo import silloApp` raises
`ImportError` at import time, before any of your code runs.

0.0.2a1 briefly kept the old name working behind a `DeprecationWarning`. If you are on that release, run your suite with `-W error::DeprecationWarning` to find every remaining use before moving on.
</Aside>

Nothing else in the constructor changed: every argument, and every method on
the returned application, is the same. The only other visible difference is
that `str(app)` now reads `<SilloApp: title>`, which matters if you assert on
dev-server output or log lines.

## Why uv is recommended

Recommended, not required, and recommended strongly. It resolves and installs
an order of magnitude faster than pip, produces a lockfile without a separate
tool, installs the Python interpreter itself when you need a version you do not
have, and runs commands inside the environment without an activate step to
forget.

Poetry gives you the lockfile and the dependency groups but not the speed or
the interpreter management. `venv` and `pip` give you neither, in exchange for
needing nothing installed.

If your team already has a workflow, keep it. Nothing in Sillo reads a
lockfile or shells out to a package manager, so the choice is yours alone.
